# SortMySkills AI Reliability + Supabase Persistence Refactor

You are working inside the existing SortMySkills Next.js app.

This is a reliability and infrastructure hardening task.

Do not rebuild the app.

Do not break authentication.

Do not break any existing user-facing functionality.

The goal is to make AI/API usage more reliable by using separate Groq API keys per feature, adding fallback behavior, moving rate limits and heavy analysis data to Supabase, and improving weak points without changing the core product flow.

---

## Absolute Safety Rules

Do not touch authentication behavior.

Do not modify login, signup, forgot password, reset password, OTP/email verification, Supabase auth session handling, auth middleware, protected routes, auth redirects, profile sync, or auth-related environment variables.

Do not break these routes:

- Dashboard
- Why No Reply
- Career Analyser
- Resume Builder
- Interview Packs
- Profile
- API Roadmap
- API Why No Reply
- API Resume Builder
- API JD Translate

Do not expose any API key to the browser.

Do not place Groq API logic inside client components.

All AI calls must remain server-side only.

---

## Current Problem

The app currently uses one shared Groq API key across multiple AI features.

This creates a reliability problem.

If one feature exhausts or overloads the shared key, all AI features can fail.

The app also has no strong fallback system.

The current rate limiter uses local memory, which is unsafe for production because it resets on server restart and does not work reliably across serverless instances.

Some important user data is stored in localStorage, which is not enough for long resumes, job descriptions, generated roadmaps, and AI outputs.

---

## Target Result

Implement a safe AI infrastructure layer with:

- Separate Groq API keys per feature
- Fallback keys per feature
- Fallback models per feature
- Shared Groq caller utility
- JSON parsing and repair retry
- Supabase-backed rate limiting
- Supabase-backed analysis persistence
- AI request logging
- Graceful failure messages
- No broken auth
- No broken existing functionality

## Step 4: Fallback Rules

Fallback should trigger when:

- Groq returns rate limit error
- Groq returns server error
- Groq request times out
- Network request fails
- Response is empty
- Response JSON parsing fails

Fallback should not trigger when:

- User input is invalid
- Required fields are missing
- The request violates validation rules
- The user has exceeded app-level rate limits

Use this order:

1. Primary key with primary model
2. Fallback key 1 with primary model
3. Fallback key 2 with primary model
4. Primary key with fallback model
5. Fallback key 1 with fallback model
6. Legacy GROQ_API_KEY if configured

Limit total attempts so requests do not hang forever.

Use clear timeouts.

Why No Reply can use a shorter timeout.

Roadmap and Resume Builder can use a longer timeout.
